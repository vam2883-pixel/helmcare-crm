## ФАЗА 0 — ФУНДАМЕНТ БЕЗОПАСНОСТИ И ДАННЫХ (P0, обязательный пролог)

Без этого всё остальное строится на песке.

### 0.1 Настоящая авторизация (Supabase Auth)
- **Цель:** убрать пароли из бандла; вход по личным учёткам (§51)
- **Переиспользуем:** AuthProvider, LoginPage, ролевую модель секций (`roles` в NAV)
- **Изменения:** Supabase Auth (email+password), таблица `profiles` (user_id, name, role, avatar); маппинг ролей CEO/COO/CommDir/Marketing/FranchiseSales/DOOHSales/TechManager/Technician/Finance/Legal/Dev/Ops/Admin
- **БД:** `profiles` + триггер on auth.users
- **Риск:** средний — переезд сессий; демо-вход оставить за фиче-флагом для локалки
- **Приёмка:** в бандле нет паролей; вход только по учёткам; роль из БД

### 0.2 Настоящие RLS-политики
- **Цель:** закрыть публичную запись в БД (риск №1 аудита)
- **Изменения:** политики: чтение — authenticated по ролям; запись — по ролям (машины: Ops/Admin; лиды: Sales; и т.д.). Анонимному ключу — только чтение витринных данных или ничего
- **Риск:** высокий (можно отрезать себе доступ) — накатывать поэтапно, с проверкой каждой таблицы
- **Приёмка:** запись анонимным ключом через curl возвращает 401/403

### 0.3 Валюта Rp и разметка данных
- **Цель:** §49–50, §62 — честные данные
- **Изменения:** хелпер `fmtMoney(amount, currency='IDR')`; замена всех 58 «₽»; колонка `currency` в денежных таблицах; демо-строки в campaigns/contractors/legal/clients/… либо удалить (после подтверждения), либо пометить `is_demo`; бейдж «ДЕМО» в UI на демо-данных
- **Приёмка:** grep «₽» по src = 0; каждый экран либо реальные данные, либо явный бейдж ДЕМО

### 0.4 Регулярный импорт продаж
- **Цель:** KPI не протухают
- **Изменения:** страница «Импорт» (Admin): загрузка xlsx → парсинг в браузере → upsert машин/моек/помесячных; журнал импортов. Параллельно выяснить API вендинговой платформы (в Excel есть Document Number — платформа явно имеет экспорт)
- **БД:** `import_log`
- **Приёмка:** пользователь сам загружает свежий xlsx, цифры обновляются, руками ничего не правится

## ФАЗА 1 — ОПЕРАЦИОННОЕ ЯДРО (P0)

### 1.1 CEO Command Center (§5–7)
- **Переиспользуем:** OverviewSection, DrillCard, графики
- **Изменения:** убрать хардкод; KPI: активные автоматы X/80, uptime-прокси, мойки сегодня/MTD, **мойки/активный автомат/день** (главная цифра: факт · цель 5.0 · % · тренд WoW), выручка MTD (мойки/DOOH/франшиза), критические алерты, просроченные задачи. Цели — в `app_settings.targets` (конфиг). Блок **CEO ACTION REQUIRED** — генерация алертов из данных (36 offline; HC-xxx <1 мойки/день 14 дней; лид без активности 48ч; договор истекает; задача просрочена), каждый кликабелен → объект
- **БД:** `app_settings` расширить (targets, thresholds)
- **Приёмка:** §68 — CEO отвечает на вопросы «сколько работает, сколько моек, движемся ли к 5» за 30 секунд без Excel; ни одного демо-числа

### 1.2 Классификация автоматов + Network Wash Performance (§8–9)
- **Переиспользуем:** MachinesSection, machine_monthly
- **Изменения:** расчёт washes/day по активным; классы CRITICAL(<1)/WEAK(1-2)/DEVELOP(2-4)/GOOD(4-7)/TOP(>7), пороги в конфиге; распределение по классам с drill-down; фильтры Today/7d/30d/MTD; отдельно платные/промо мойки (в импорте разделять Free/Coupon от платных)
- **БД:** wash_stats: колонки `w_paid`, `w_promo` (миграция), пересчёт при импорте
- **Приёмка:** клик «CRITICAL: 12» открывает 12 автоматов; в шапке «Paid washes/active/day»

### 1.3 Machine 360 (§12)
- **Переиспользуем:** существующий drill автомата
- **Изменения:** секции Overview/Performance/Trend (график 7/30/90 из machine_monthly + daily)/Technical(заглушка честная)/Finance(DATA INCOMPLETE до внесения аренды)/Tasks/Recommendation
- **БД:** machines: `installed_date`, `responsible`, `rent_amount`, `rent_currency`
- **Приёмка:** карточка отвечает «что это за точка и что с ней делать»

### 1.4 Глобальный движок задач (§36–38)
- **Цель:** SIGNAL → OWNER → TASK → DEADLINE → RESULT
- **Изменения:** таблица `tasks` (department, object_type, object_id, title, assignee, creator, priority, deadline, status NEW/IN_PROGRESS/BLOCKED/DONE, kpi_link, comments jsonb); OVERDUE вычисляется; блок «Мои задачи» на каждом дашборде (сегодня/просрочено/неделя/высокий приоритет); создание задачи из алерта в 1 клик
- **Приёмка:** алерт CEO превращается в задачу с ответственным и дедлайном; просрочка видна везде

### 1.5 Технические тикеты + SLA (§13–16)
- **Переиспользуем:** TechnicalSection, technicians
- **Изменения:** `tech_incidents` (machine, problem, source, priority, sla_deadline, status NEW→CLOSED, assignee, resolution, resolved_at, repeat_flag); SLA конфиг (4/12/24/72ч); авто-алерт при просрочке SLA; расчёт lost washes/revenue по средним до поломки (пометка ESTIMATE); MTTR
- **Приёмка:** офлайн-автомат → тикет → техник → закрытие; отчёт MTTR/SLA compliance

### 1.6 Data Quality (§48)
- **Изменения:** вычисляемый экран: автоматы без локации (сейчас 28!), без ответственного, лиды без next action, договоры без даты истечения…; DATA QUALITY SCORE у CEO/Admin
- **Приёмка:** список проблем кликабелен, счёт растёт по мере чистки

## ФАЗА 2 — КОММЕРЧЕСКИЙ ДВИЖОК (P0/P1)

### 2.1 Дашборд коммерческого директора (§17–18)
Три блока: WASHES (факт/цель/динамика, слабые локации, кандидаты на буст/релокацию), DOOH, FRANCHISE. Цель 90 дней: 7–8 моек/активный автомат/день, помесячные вехи в конфиге.

### 2.2 Дисциплина франшизной воронки (§20–22)
- **Переиспользуем:** FranchiseSection (13 этапов сохраняем)
- **Изменения:** поля лида: source, campaign, responsible, next_action, next_action_date, deal_value, probability, история контактов; алерты: нет активности 48ч, нет next action, КП без фоллоу-апа; прогноз: weighted pipeline, конверсии по этапам, цикл сделки
- **Приёмка:** у каждого активного лида есть ответственный + следующее действие + дата; воронка считает ожидаемую выручку месяца

### 2.3 DOOH: инвентарь, occupancy, пайплайн (§19, 23–25)
- **Переиспользуем:** AdSlotsSection, contractors
- **Изменения:** `dooh_inventory` (machine, slots_total — конфигурируемо, не хардкод 4), `dooh_contracts` (advertiser, slots, machines, value, start/end, invoice_status), пайплайн Lead→Renewal; occupancy % (сеть/локация); сценарии выручки 25/50/75/100%
- **Приёмка:** CEO видит occupancy и MRR рекламы; договор истекает → алерт

### 2.4 Location Score + релокации (§10–11)
- **Изменения:** score 0–100, веса в конфиге (`app_settings.location_score_weights`); рекомендация KEEP/BOOST/PROMO/WATCH/RELOCATE; `relocations` workflow (Candidate→…→Completed) со снимками производительности до/после 7-14-30 дней
- **Приёмка:** менеджмент видит, дала ли релокация эффект, цифрами

### 3.1 KPI-движок (§42–45)
`kpis` + `kpi_results`: иерархия компания→отдел→менеджер; факт из данных CRM автоматически, где возможно; правила компенсации ком. директора в `compensation_rules` (база 30 млн Rp, бонусы конфигом, флаг SALARY REVIEW ELIGIBLE при 7–8 мойках + DOOH-план + франшиза-план — без автоизменения зарплаты)

### 3.2 Четверговый отчёт (§39–41)
Автосборка WEEKLY EXECUTIVE REVIEW из данных (wins/problems/decisions, по отделам); `weekly_commitments` (3–5 обязательств на руководителя, DONE/NOT DONE на следующем четверге, completion rate)

MTD run-rate для моек/выручки, weighted pipeline для франшизы/DOOH; трекер цели 5→7–8 с траекторией; методика расчёта показана прямо в UI

## Что НЕ делаем (осознанно)

- Не переписываем App.jsx целиком — выносим секции постепенно, при доработке
- Не строим AI-прогнозы — только прозрачный run-rate (§56)
- Не выдумываем телеметрию/uptime — прокси с пометкой ESTIMATED до интеграции с платформой
- Не считаем прибыльность без расходов — DATA INCOMPLETE
- Не делаем клиентский модуль без идентификаторов клиентов
